# Evidence-gated merges with a human-owned meta surface

## Context and Problem Statement
FerroAstro is built mostly by agents. Under ORG-009 as first written, every agent-authored PR needed a human approval, so a maintainer had to read every change, and nothing checked that the approval meant anything. On 2026-10-14 the maintainer chose **"data-gated + human-owned meta"** (#12): agents open, lead and merge PRs on evidence alone, and humans own the small set of files that define what counts as evidence.

The red-team review (Journal #9, §2) showed what this needs to be honest:

* **C1.** At least eight places in the docs still said a human must approve. Agents follow whichever rule lets them pass, so all of them change in this one PR.
* **C2.** If a required check runs the PR head's workflow or scripts, a PR can switch off its own evidence (`trace.py` returning 0, `paths-ignore`, `deny.toml` exceptions, regenerated manifests).
* **C3.** A golden value and its citation can be edited together, and a computed-reference golden can be regenerated by a modified runner in the same PR.
* **C4.** Under zero review, a `Signed-off-by:` trailer is text an agent can type. It is not evidence of a person.
* **H1–H3.** Tolerances can be widened with a fluent rationale; tests can be disabled through `#[ignore]`, `cfg` or nextest profiles; labels set by the PR author can count as evidence; and an auto-merge can race a `hold`.

The written rule must never claim more than CI checks. How do we let evidence decide merges without letting a PR change the evidence?

## Decision Drivers
* A PR must not be able to weaken the checks that judge it, the data they compare against, or the record of who is responsible for it.
* Human attention goes where it cannot be replaced: the definition of evidence, and judgement calls the ratchet flags.
* No delay once the checks pass (maintainer decision 2026-10-14).
* Every rule has a named check. Where a rule depends on a GitHub setting that only a maintainer can apply, the docs say so, and the requirement is not met until the setting is applied.

## Considered Options
* **Human approval on every agent PR** (ORG-009 as first written).
* **Data-gated, human-owned meta**: evidence checks decide; CODEOWNERS review only on the meta surface; a base-branch ratchet; a maintainer-only hold; signed commits with delegation records.
* **Data-gated only**: evidence checks decide, with no human-owned files.

## Decision Outcome
Chosen option: **data-gated, human-owned meta**, because it is the only option where neither agents nor humans are the bottleneck and a PR still cannot rewrite its own evidence. "Data-gated only" fails C2 by construction. "Human approval on every PR" is what the maintainer rejected, and C4 shows it was weaker than it looked.

The pieces (requirements ORG-008, ORG-009, ORG-011, TST-004, TST-006):

1. **Meta surface (ORG-011).** `.github/CODEOWNERS` lists the files that define the evidence. The ruleset requires Code Owner review and otherwise 0 approvals. Owners are the logins in `.github/governance/maintainers.txt`, and pytest keeps the two in step and checks CODEOWNERS against the ORG-011 list. CODEOWNERS cannot see fields, so field-level rules (requirement `status` and `verified_by_gate`; PHY/NUM `statement` and `acceptance`, where values and tolerances live) go through the ratchet.
2. **Ratchet (TST-006, TST-004).** `tools/ratchet.py` compares the head with `git merge-base(base, head)`, the tree the PR branched from, never with the current tip of `main`: whatever `main` gained since the branch point (tests, vectors, requirement status) would otherwise read as removed by the PR, and every PR that is behind `main` would fail. It classifies each finding. **approval** findings pass only when a maintainer's latest review approves the current head SHA. They cover: tolerance widened, kind downgraded, |Δvalue| > k·old tolerance, vector or test deleted, `blocked_by` added, executed-test count fallen, a Rust `ignore`/`cfg`/`cfg_attr` attribute or Python skip/xfail/collection gate off the allowlist in `ci/ratchet.toml` (or naming a Cargo feature the base does not declare) that is new on the item it stands on, pytest configuration under `tools/` changed, and ORG-011 field changes. A gate is keyed by file, item (the Rust item it decorates, by inline `mod` path, kind and name; the Python function or class it decorates or sits in) and text, so moving an existing gate from one test onto another is a new gate even though the counts do not change. Rust sources are scanned with comments and string literals masked out, so a test inside `/* ... */` counts as deleted and attributes on one line are seen. Python tests and gates are taken from the parsed module, not by pattern: a test wrapped in a string, put under `if False:` or `del`-ed counts as deleted, and `__test__`, `collect_ignore` and `collect_ignore_glob` assignments and `pytest.exit` are gates. **What is detected** (each form pinned by a test in `tools/tests/test_ratchet.py`): in Rust under `crates/`, any `ignore`/`cfg`/`cfg_attr` attribute (outer or inner, whitespace-normalised, so `# [ignore]` counts; `cfg_attr(..., ignore)` too) off the allowlist or naming an undeclared feature; in Python under `tools/`, decorator-form `@pytest.mark.skip`/`skipif`/`xfail` under any alias or as bare `@mark.skip`, `pytest.skip()`/`xfail()`/`importorskip()`/`exit()` calls, unittest skips, assignments to `pytestmark`/`__test__`/`collect_ignore`/`collect_ignore_glob`, `def pytest_*` hooks, and an unparsable file. **What is not detected** (each pinned by a `test_known_gap_*` test asserting no finding, and listed in TST-006 notes): skips or `__test__` built at run time; a new call to an existing skipping helper; a test that returns early, is emptied or has its assertions under Rust `if false` (Python and Rust); deleting a pytest test outside the default naming (a `unittest.TestCase` method in a class not named `Test*`); an allowlisted gate that hides a Rust test from the PR tier (a declared-feature `cfg`, or `ignore = "data..."` on a test that needs no data), and a test file moved out of the build or a dropped `mod` line, both caught only by `ratchet (test count)`, whose head listing is the PR's own; a gate moved between same-named Rust fns of one module; anything outside `crates/` (Rust) and `tools/` (Python); pytest outcome exceptions raised directly (`from _pytest.outcomes import Skipped`, `XFailed`, `Exit`, `OutcomeException`); an empty `@pytest.mark.parametrize(..., [])`; `os._exit`/`sys.exit` in a test file (pytest stops with exit 0 and no summary); `__init__`/`__new__` on a `Test*` class (not collected); `@pytest.fixture` on a `test*` function (not collected, still counted as a test); a pytest hook bound by assignment (`pytest_* = ...`) rather than `def`; and Rust `#[should_panic]` on a failing test, which turns the failure into a pass (only `ignore`/`cfg`/`cfg_attr` are gate attributes, and the test still runs, so the count does not see it). There is **no executed-test count for pytest**, so an undetected Python gap is not caught at all. The follow-up issue #55 ("ratchet: close the detection gaps listed in TST-006") tracks closing them; until then the written rule claims only the detected forms. **golden** findings (value or tolerance changed) pass only with the maintainer-applied `golden-change` label and a changed evidence field. **reject** findings never pass: a computed-reference golden whose `generated_by` SHA is a commit of the same PR. Two checks: `ratchet` and `ratchet (test count)`.
3. **Hold (ORG-009 acceptance 4).** The `hold` check fails while the `hold` label is on a PR, whoever set it (fail-safe), and after the label is removed until a maintainer removes it: the hold clears only when a maintainer's latest `unlabeled` event comes after the latest `labeled` event by anyone. Only a maintainer can clear any hold. If a non-maintainer removed the label first, a maintainer adds and removes it again. #12 says "only maintainers can set or clear"; letting anyone set a hold is a deliberate fail-safe deviation, since a hold can only block. It re-runs on every label change and push, and in the merge queue.
4. **Signed commits (ORG-008, ADR-0005 revision 2026-11-14).** Every non-merge PR commit must be signed (SSH or OpenPGP) by a key in `.github/signing/`. That key's delegation record must name the operator in the commit's `Signed-off-by` and be valid on the commit date. The committer date is chosen by whoever commits and can be backdated, so the record must also still be valid on the (UTC) date the check runs: an ended delegation cannot be reused by backdating. Early revocation is done by removing the record. The check is `signed-commits`.
5. **Base-SHA execution (C2).** The hold, ratchet and signature checkers, their configuration (`ci/ratchet.toml`), the maintainer list and the key registry are all read from a checkout of the **base** commit. The PR head is only data, and no job that runs a checker builds or runs PR code. Building runs PR code (build scripts, proc macros, test binaries) with write access to the job's workspace, so the test count is split into three jobs: `ratchet (list merge-base tests)` builds only the merge base, without any cache a PR build could have written; `ratchet (list head tests)` builds the PR; and the required `ratchet (test count)` downloads both listings by the artifact ids those jobs reported (a replaced artifact gets a new id, so the download fails closed) and judges them with the base-SHA checker. It fails if either listing job did not succeed. The head listing is produced by PR code and so is the PR's own claim; the source scan in `ratchet` (deleted tests, new gates) does not depend on it. Workflows use `pull_request`, never `pull_request_target`, with a read-only token (`contents`, `issues`, `pull-requests: read`) and actions pinned by SHA (`tools/lint_workflows.py`). The workflow YAML itself comes from the PR's merge commit, so two more things are required: `.github/` is on the meta surface, and the maintainer pins the required workflows to the default branch with a ruleset.
6. **Labels.** Agents that can open PRs can write labels, and GitHub cannot split those permissions. So the checks ignore label events by non-maintainers instead of trusting the token: a non-maintainer can set `hold` but cannot clear any hold, not even their own, and a non-maintainer's `golden-change` counts for nothing.

### Agent identities
Every "maintainer" test above tells people apart by GitHub login. **If an agent runs under a maintainer's account, it can approve, label and clear holds as that maintainer, and none of this binds it.** Agents therefore need their own GitHub accounts (or a GitHub App) with write but not admin access, and their own signing keys. Until then this is a known residual risk. The setting cannot be made in-repo, so it is listed under maintainer actions.

### Bootstrapping and open PRs
When this PR is opened, `main` has no checkers yet, so the new workflows fall back to the head copy and print a notice. The fallback runs only while the base lacks the script: once this PR merges, no later PR can trigger it. This PR is itself on the meta surface.

New required checks do not deadlock open PRs:
* `hold`, `ratchet`, `ratchet (test count)` and `signed-commits` run on `pull_request` events, which use the workflows of the PR's merge commit with the current `main`. Any push, rebase, or close-and-reopen of an open PR therefore runs them. For `hold`, so does a label change.
* `signed-commits` starts in `report` mode: every open PR's commits are unsigned, and the check passes with warnings. The maintainer switches to `enforce` only after registering the agents' keys. Commits already open at that point are either re-signed by their authors or listed in `grandfathered`.
* `ratchet` and `ratchet (test count)` compare each PR with its own merge base, so a PR that is behind `main` (on 2026-11-14 #18 is 25 commits, 15 of them merges, behind `main` 86ae6b1) is judged only on its own changes. Merging this PR, which adds tests, does not give any open PR a "test deleted" finding, and "Require branches to be up to date" can stay off. `tools/tests/test_ratchet.py::test_stale_branch_is_compared_with_its_merge_base` reproduces the case.
* A `ratchet` finding on an open PR is satisfiable: a maintainer approves the head SHA, or applies `golden-change` and the PR adds evidence. Run on 2026-11-14 against the PRs open on `main` (this PR's `tools/ratchet.py` and `ci/ratchet.toml`, each head compared with its merge base with `main` 86ae6b1), only #18 is open there: head 1a5cc82, merge base 86ae6b1 (up to date with `main`), **37 findings**, all `approval`, none `golden` or `reject`. They are 4 NUM `statement`/`acceptance` edits (NUM-007, -009, -022, -024); 14 new `#[ignore]` gates (`nightly_speed_table.rs` 1, `mu_star_rate.rs` 1, `irk16_checks.rs` 3, `abm_runs.rs` 2, `nightly_abm_subbotin.rs` 1, `nightly_ephemeris_mode.rs` 2, `nightly_wh_irk16.rs` 3, `viewer_physics.rs` 1), all moving tests out of PR CI, of which 5 hide tests recorded as failing ("nightly known failure" ×3 in `irk16_checks.rs`, "fails its pre-registered bound (WP25 C3b, NEEDS HUMAN REVIEW)" in `mu_star_rate.rs`, "fails its pre-registered PROVISIONAL bound (WP24 B2, NEEDS HUMAN REVIEW)" in `abm_runs.rs`); and 19 `cfg` gates (18 `feature = "simd"`, 1 `not(feature = "simd")`, one finding per gated item) on the `simd` feature that #18 itself adds, which the base does not declare. One maintainer approval of #18's head clears all 37, and also any `ratchet (test count)` finding (not run here: it needs the nextest listings), so the approver is approving all of them. #54 targeted `m5-performance` and has merged there; these checks and rulesets do not apply to that branch. PRs that touch the meta surface (#18 changes `.github/workflows/ci.yml`, `.config/nextest.toml`, `ci/`, `clippy.toml`, `tests/vectors/` and `tools/pyproject.toml`) need a Code Owner approval from a maintainer **other than the PR author's account**. While agents open PRs as one maintainer, the other maintainer has to approve.

### Repository settings (maintainer actions)
These cannot be made in-repo. Until they are applied, ORG-009 and ORG-011 are not met.
1. Ruleset on `main` ("Protect Main"): keep deletion, non-fast-forward and pull-request rules. Set required approvals to **0**, turn on **Require review from Code Owners**, turn on **dismiss stale approvals on push**, and leave **require approval of the most recent push** off.
2. Required status checks (job names, source GitHub Actions): `hold`, `ratchet`, `ratchet (test count)`, `signed-commits`, `dco (Signed-off-by on every commit)`, `pr-title (Conventional Commits)`, `rust (fmt, clippy, nextest, doctest, deny, doc)`, `msrv (rust-version 1.85)`, `wasm32 (real, core, erfa, time, integrators, forces, analytic, frames, ephem, eih)`, `python (ruff, mypy, pytest, trace)`, `reuse lint`. Do not require "up to date with base": that would add a rebase cycle.
3. Org-level ruleset "Require workflows to pass", targeting this repository's `main`, with `hold.yml`, `ratchet.yml`, `signatures.yml` and `ci.yml` pinned to `refs/heads/main`. This is what makes a PR's edit to these files ineffective. Whether this is available on the org's plan is UNVERIFIED. If it is not, `.github/` on the meta surface is the only protection.
4. Settings → Actions → General: set the default `GITHUB_TOKEN` permission to **read**, and turn off "Allow GitHub Actions to create and approve pull requests".
5. Merge queue: either **off** (the default here, which meets acceptance 5, but a hold set while a merge is in flight is not seen), or **on** with build concurrency 1, minimum and maximum group size **1**, and wait time **0**. Group size 1 is required by `tools/governance.py`. Every required workflow already has a `merge_group` trigger.
6. Agent identities: agents use their own accounts or a GitHub App with write (not admin, not maintain) access. They are not listed in `.github/governance/maintainers.txt`, and they are not bypass actors on any ruleset. Ruleset bypass is limited to repository admins "for pull requests only", or nobody.
7. Labels `hold` and `golden-change` exist (the latter does). Register each agent's signing key and delegation record in `.github/signing/` by a maintainer-reviewed PR, then switch `delegations.toml` to `mode = "enforce"`.
8. After 1–7: run the canary PRs (Confirmation), then add the pinned gates to `PINNED_GATES` in `tools/trace.py` (ADR-0010 condition 3).

### Consequences
* Good: agents merge non-meta work without waiting, and humans review only evidence definitions and flagged weakenings.
* Good: every rule in ORG-008/009/011 and TST-004/006 names the check that enforces it.
* Bad: the ratchet's test matching is by name, so renames need approval; the allowlist needs upkeep.
* Bad: the test count builds the workspace twice, the merge base (cold, no cache, by design) and the head, each about the cost of the `rust` job, in parallel jobs. It is skipped in the merge queue. The `pull_request_review` trigger (needed so an approval re-evaluates the approval findings) also reruns both builds on every review; skipping them on some reviews would leave a skipped, hence passing, required check, so the cost is accepted.
* Bad: until the maintainer actions are applied, and agents have their own accounts, the merge policy here is a description of intended enforcement, not enforcement. ORG-009 notes say so.
* Not covered here (red-team §2 controls 4 and 5, H4, H5): signed oracle images, PDF hashes for published vectors, mandatory oracle runs on physics paths, adequacy of self-cited requirements, and OPEN-ITEMS ticks (`OPEN-ITEMS.md` is not on the meta surface; a tick can arm or disarm `blocked_by` rows). Mutation testing (control 7) is written into TST-006 from M2 and not implemented yet. The 12–24 h queue delay (control 6) was rejected by the maintainer on 2026-10-14.

### Confirmation
* pytest: `tools/tests/test_ratchet.py`, `test_governance.py`, `test_verify_signatures.py` (each weakening is detected, overrides work only for maintainers on the head SHA, CODEOWNERS matches ORG-011 and the maintainer list, an end-to-end SSH-signed commit passes and an unsigned one fails in `enforce` mode).
* `tools/lint_workflows.py` on `hold.yml`, `ratchet.yml` and `signatures.yml`.
* After the rulesets are applied, the maintainer runs the canary PRs of ORG-011's acceptance: one per listed path (blocked without approval), one outside the surface (merges on checks), one widening a tolerance (fails `ratchet` until approved), one with `hold` cleared by a non-maintainer (still held), and one unsigned commit after `enforce` (fails `signed-commits`). The results are recorded on #12, and `tools/trace.py` `PINNED_GATES` gains the pinned gates.
